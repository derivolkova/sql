## Задание 2. Четыре аналитических запроса

**2.1. Общая выручка по категориям**

``` sql
SELECT 
    category,
    SUM(quantity * unit_price * (1 - discount_pct / 100)) AS total_revenue
FROM sales_var7
GROUP BY category
ORDER BY total_revenue DESC;
```

**2.2. Топ-3 клиента по количеству покупок**

``` sql
SELECT 
    customer_id,
    COUNT(customer_id) AS purchase_count,
    SUM(quantity) AS total_quantity
FROM sales_var7
GROUP BY customer_id
ORDER BY purchase_count DESC, customer_id  
LIMIT 3;
```

**2.3. Средний чек по месяцам**

``` sql
SELECT 
    toYYYYMM(sale_timestamp) AS month,
    round(AVG(quantity * unit_price), 2) AS avg_check
FROM sales_var7
GROUP BY month
ORDER BY month;
```

## Задание 6. Контрольные вопросы.

**Почему LowCardinality(String) эффективнее обычного String для столбца category?**

LowCardinality(String) эффективнее, потому что при малом количестве уникальных значений данные сжимаются за счёт словаря и занимают меньше места на диске.

**В чём разница между ORDER BY и PRIMARY KEY в ClickHouse?**

В ClickHouse PRIMARY KEY (является индексом для быстрого поиска данных) не обязан быть уникальным и используется для пропуска ненужных гранул данных, а ORDER BY - обязательная сортировка

**Когда следует использовать ReplacingMergeTree вместо MergeTree?**

Когда нужно хранить только последнюю версию строки

**Почему SummingMergeTree не заменяет GROUP BY в аналитических запросах?**

 Без GROUP BY можно получить частично просуммированные или непросуммированные данные.
 
**Что произойдёт, если не выполнить OPTIMIZE TABLE FINAL для ReplacingMergeTree?**

Старые версии строк останутся в таблице. При обычном SELECT выводятся все версии.
